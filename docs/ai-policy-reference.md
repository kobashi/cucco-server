## 1. 実装するメソッド

`BasePolicy` を継承し、必要なものだけ上書きする。**すべて同期関数**で、
**即座に返す**こと(サーバーの中で動くので、待つと卓全体が止まる)。

| メソッド | 呼ばれる場面 | 返す | 未実装時 |
|---|---|---|---|
| `decide_change(own_rank, alive_count)` | 自分の手番 | `True`=交換(カンビオ) / `False`=しない | **これか `decide_change_ctx` のどちらかは必須** |
| `decide_cucco_declare(own_rank, alive_count)` | クク札を持っている自分の手番・「どうぞ」 | `True`=クク宣言 | 常に `True` |
| `decide_continue(chips, required_chips)` | 子供の時間に敗者になった | `True`=払って続行 | 常に `True` |
| `decide_change_ctx(ctx)` | 上と同じ場面(**こちらが優先**) | 同上 | `decide_change` に委譲 |
| `decide_cucco_declare_ctx(ctx)` | 同上 | 同上 | `decide_cucco_declare` に委譲 |
| `decide_continue_ctx(ctx)` | 同上 | 同上 | `decide_continue` に委譲 |
| `declare_cucco_eagerly(ctx)` | クク札を**持った瞬間**(手番を待たずに宣言するか) | `True`=即宣言 | `False`(**中間の席ではクク を取られる**。§3) |

`_ctx` 版を実装すると、下の `PolicyContext` すべてが使える。両方実装した場合は
`_ctx` 版が呼ばれる。

> [!NOTE]
> **例外を投げても対局は止まらない。** その判断だけ既定値(交換しない / 続行する /
> クク宣言する)で進み、サーバーのログに理由が残る。ただし黙って弱くなるので、
> ログは確認すること。

## 2. 判断材料(`PolicyContext`)

| フィールド | 型 | 中身 |
|---|---|---|
| `own_rank` | `str` | 自分の手札(`"0"`〜`"12"` か特殊札名) |
| `alive_count` | `int` | そのディールに残っている人数(自分を含む) |
| `deal_number` | `int` | そのポット内のディール番号(1始まり)。**1〜3が子供の時間** |
| `pot_chips` | `int` | 場に積まれているチップ |
| `my_chips` | `int` | 自分の持ちチップ |
| `is_dealer` | `bool` | 自分が親か。交換相手を知りたいなら `ctx.exchange_target` を見る(§3) |
| `unseen_counts` | `dict[str, int]` | **まだ見えていない札**の枚数(札名→枚数)。自分の手札は除いてある |
| `known_held` | `dict[str, str]` | 公開されて分かっている他家の手札(player_id→札名)。分かっている分だけ |
| `turn_actions_this_deal` | `int` | そのディールでこれまでに行われた手番宣言の数 |
| `required_chips` | `int` | 続行に必要なチップ(`decide_continue_ctx` のときだけ意味がある) |
| `my_id` | `str` | 自分の player_id(`turn_order` の中で自分を見つけるのに使う) |
| `chips` | `dict[str, int]` | **全員の持ちチップ**(公開情報。狙い撃ちの材料) |
| `turn_order` | `tuple[str, ...]` | このディールの手番順。**親が最後**で循環しない(§3) |
| `disqualified` | `frozenset[str]` | このディールで失格した席 |
| `acted_this_deal` | `frozenset[str]` | もう手番宣言を済ませた席 |
| `exchanges_this_deal` | `tuple[ExchangeRecord, ...]` | このディールで起きた交換の記録(起きた順) |
| `own_card_original` | `bool` | 今の札の**元の持ち主が自分**か。配られたままなら `True`、一度でも交換すれば `False`。猫がらみの失格は「要求者の札の元の持ち主」に落ちるので、`True` のまま交換を仕掛けると自爆しうる |

`ExchangeRecord` の中身(`from cucco.ai.context import ExchangeRecord`):

| | 中身 |
|---|---|
| `requester` | 要求した席。カンビオ宣言には専用のイベントがないので、**動いた席が分かるのはここだけ** |
| `target` | 要求された席。`None` なら山札と交換した |
| `result` | `"accepted"` / `"refused"` / `"deck_exchange_accepted"` / `"deck_draw_refused"` |
| `revealed_rank` | 拒否で公開された札(人間・馬・猫・家)。なければ `None` |

> [!NOTE]
> 馬・家の拒否連鎖では1つの要求に対して複数件記録される。`requester` は連鎖の
> あいだ変わらないので、「誰が動いたか」はそれで数えられる。

補助:

| | 返す |
|---|---|
| `ctx.is_child_time` | 子供の時間(1〜3ディール目)か |
| `ctx.unseen_total` | 見えていない札の合計枚数 |
| `ctx.unseen_weaker_than_own()` | そのうち**自分より弱い**札の枚数 |
| `strength_of(rank)` | 札の強さ(数が大きいほど強い)。`from cucco.ai.context import strength_of` |
| `ctx.chip_leader` | チップ**単独**首位の player_id。同点首位なら `None`。自分が首位なら自分の id |
| `ctx.exchange_target` | 自分がカンビオしたときの交換相手。`None` なら**山札**(§3) |
| `ctx.unacted_before_me()` | 自分より前で未行動の生存席 = **自分を狙える席**。空なら誰にも奪われない |
| `ctx.last_exchange` | 直近の交換の記録(`ExchangeRecord` か `None`) |
| `ctx.was_taken_from(pid)` | その席が交換の**対象**にされ、交換が成立したか |

### 見えないもの

- **他人の手札**(公開されたものを除く。`known_held` がその全部)
- **山札の並び**(次に何が来るかは誰にも分からない)
- 他の方策の内部状態、他の卓の状況

## 3. 手番の順と交換相手

ここを知らないと交換判断とクク宣言を正しく書けない。正は
[rules/final_rules.md](rules/final_rules.md)(「ディールの進行」「クク宣言」)。

```
order = [第1, 第2, 第3, 親]      ← 循環しない
          ↓    ↓    ↓    ↓
交換相手: 第2   第3   親   山札
```

| | |
|---|---|
| 手番順 | 親の次の席から始まり、**親が最後** |
| 交換相手 | **次の席**(自分より後ろで、最初に失格していない席) |
| 末尾(親)の交換相手 | **山札**(ルール上「山札を右隣のプレイヤーとみなす」) |
| 自分を狙える相手 | **直前の1席だけ**(循環しないので第1プレイヤーを狙う席は存在しない) |

### 親の交換相手は山札(入手できる札が別物になる)

親かどうかではなく、**入手できる札の分布が別物になる**ことが判断に効く。

| 山札から引いた札 | どうなるか |
|---|---|
| クク | 拒否される(手札維持)。**入手できない** |
| 馬・家 | 引き直し。**入手できない** |
| 人間 | **引いた本人が失格**(対人交換なら要求した側が失格、という向きが逆になる) |
| 猫 | 自分の札の元の持ち主が失格(自分が元の持ち主なら自爆) |
| 道化 | 例外的に**最強**(ククより上)になる。対人交換で受け取ると即失格なのと真逆 |

つまり親の交換は「弱い札を掴まされる危険が低い代わりに、最強札も引けない」。
対人交換と同じ閾値で判断すると合わない。

> [!NOTE]
> **交換相手を知りたいなら `ctx.exchange_target is None` を見る。**山札と交換する
> のは正確には「手番順で最後に生き残っている席」で、通常はそれが親だが、親が
> ディール途中で失格すると別の席が引き継ぐ(馬・家の拒否連鎖が最後尾に届いた
> 場合も山札へ切り替わる。[rules/final_rules.md](rules/final_rules.md)
> 「親の山札交換における効果の連鎖」)。そのプレイヤーの `is_dealer` は `False`
> のままになる。
> 実測(22,300判断)では、山札が相手になった6,174件のうち親でない席は**14件
> (0.23%)**。頻度は低いので `is_dealer` でもほぼ合うが、`exchange_target` なら
> ただで正確になる。逆向きの取りこぼし(親なのに相手が人)は0件だった。

### クク を持って自分の手番を待つと、直前の席に取られる

クク は交換を**拒否できない**(下の早見表)。自分を狙えるのは直前の1席だけなので、
危険は席によって違う。

| 席 | 待ったときの危険 |
|---|---|
| 第1プレイヤー | **なし。**前に席がないので、自分の手番より先に狙われない |
| 中間の席 | **直前の1席がカンビオを宣言すると、そのまま渡る** |
| 親 | 「どうぞ」の場面で宣言できる(自分の手番は最後尾なので、ここが他プレイヤーが動く前の唯一の機会。第一手番のカンビオはこれに割り込めない) |

`declare_cucco_eagerly(ctx)` を `True` にすると、手番を待たず**持った瞬間**に
宣言する(`deal_started` と交換成立の直後に呼ばれる)。既定は `False` で、これは
ベースラインの挙動を固定するためなので、**中間の席ではクク を取られる**。内蔵の
`counting_aggressive` / `counting_conservative` は `True`。

> [!NOTE]
> 即宣言が常に最善とは限らない。奪われる危険があるのは
> **`ctx.unacted_before_me()` が空でないあいだだけ**で、空になれば開示まで誰も
> 自分を狙えない(狙えるのは直前の1席だけなので)。損得の立て方は
> [ai-advanced-policies.md](ai-advanced-policies.md) の観点6。

### 狙い撃ち: 誰が負けるかを選ぶ

クク宣言は誰かを直接倒すわけではない。**凍結した瞬間の最弱者が敗者になる**だけ
である。だから宣言は「いつ凍結するか」を選ぶ武器として使える。

待てる窓は席で決まる。**自分の手番を過ぎれば誰も自分を狙えない**(狙えるのは
直前の1席だけ)。そこから開示までが、安全に様子を見られる区間になる。

| 使う材料 | 何が分かるか |
|---|---|
| `ctx.chips` / `ctx.chip_leader` | 誰を狙うか(チップ首位) |
| `ctx.was_taken_from(pid)` | その席が交換の**対象**にされ成立したか。要求した側は自分の札を弱いと判断して動いているので、対象にされた席の新しい札は弱い可能性が高い |
| `ctx.unacted_before_me()` | 待てるか、それとも今すぐ宣言しないと取られるか |
| `ctx.is_child_time` | 子供の時間の敗者はチップを払って残るだけ。**大人の時間(4ディール目以降)なら敗者はポットから脱落する** |

内蔵の **`counting_sniper`** がこれをやる(`counting_conservative` を継承し、
宣言のタイミングだけ変えたもの)。動く見本は
[`docs/examples/policy_sniper.py`](examples/policy_sniper.py)。

```python
def _declare_now(self, ctx) -> bool:
    if ctx.unacted_before_me():
        return True                      # 取られる前に撃つしかない
    return any(ctx.was_taken_from(pid) for pid in self._rich_seats(ctx))
```

狙い先を**単独首位**(`ctx.chip_leader`)ではなく「**自分以上**」にするのが肝。
ゲーム開始直後は全員同点で `chip_leader` は `None` を返すので、首位1人に絞ると
いちばん長い序盤がまるごと死ぬ。これだけで発火が4.4倍になる。

> [!WARNING]
> **発火するようになっても、勝率には出なかった。**400ゲームの実測で、クク を
> 持った瞬間の判断2,300回の内訳は「取られる前に撃つしかない」1,264回(55%)、
> 「待つ」960回(42%)、**実際に狙って凍結した 75回(3.3%、5.3ゲームに1回)**。
> 条件を絞った版(24ゲームに1回)の4.4倍まで増えている。それでも確認走行
> 7,000ゲームでの勝率差は **+0.39pt(SE 0.40pt)で有意差なし**。
>
> つまり**頻度は足りているのに効いていない**。待ち方をこれ以上いじっても伸びない
> と思われる。疑うべきはむしろ:
>
> - **狙い先**(「自分以上」でよいのか。倒して意味があるのは誰か)
> - **「対象にされた席は弱い」という推定そのもの**。要求した側が弱いと判断した
>   のは自分の札であって、押しつけた先がそのディールの最弱になるとは限らない
> - **凍結して得をする局面の見分け**。いま最弱なのが誰かを推定せずに止めている

## 4. 札の早見表

強い順。**同じ札が2枚ずつ、全44枚**。

| 札 | 強さ | 持っているとき | 交換を要求されたとき |
|---|---|---|---|
| クク | 最強 | いつでも「クク宣言」でディールを即終了できる(宣言者は負けない) | 拒否できない。普通に交換に応じる |
| 人間 | 2番目 | — | 拒否でき、**要求した人が失格** |
| 馬 | 3番目 | — | 「スキップ」で拒否。要求は隣へ流れる |
| 猫 | 4番目 | — | 「ニャー」で拒否。要求者の札の**元の持ち主が失格** |
| 家 | 5番目 | — | 「スキップ」で拒否。要求は隣へ流れる |
| 12 〜 0 | 数の順 | — | 拒否できない |
| 桶 | 0より下 | — | 拒否できない |
| 仮面 | さらに下 | — | 拒否できない |
| 獅子 | さらに下 | — | 拒否できない |
| 道化 | **最弱** | 持っているだけなら安全 | 拒否できない。**交換で受け取った側が即失格**(渡した側は無傷)。山札から引いた場合だけは例外的に最強(ククより上)になる |

細かい条件(山札から引いた場合、道化の昇格、猫の不発、開示設定)は
[rules/final_rules.md](rules/final_rules.md)「特殊札の効果」を参照。

## 5. 書き方の型

```python
from cucco.ai.policies import BasePolicy


class MyPolicy(BasePolicy):
    """一行の説明(卓を作る画面に出る)"""

    name = "zemi_yourname"

    def decide_change_ctx(self, ctx) -> bool:
        # 自分より弱い札が、見えていない札の何割あるか
        weaker = ctx.unseen_weaker_than_own()
        share = weaker / ctx.unseen_total if ctx.unseen_total else 0
        # 弱い札が少ない = 自分が最弱になりやすい -> 交換する
        return share < 0.35

    def decide_change(self, own_rank, alive_count):
        return False   # ctx 版を使う場合の保険(呼ばれない)
```

**状態を持ちたい場合**は `__init__` を書いてよい。方策のインスタンスは
**1ゲームにつき1つ**作られる(ディールをまたいで持ち越せるが、ゲームが変わると
リセットされる)。

## 6. 手元で測る

サーバーを起動しておき、外部クライアントとして自分の方策を走らせる。
**`--policy-dir` で `policies/` が読み込まれる**ので、自分の方策名がそのまま使える。

```bash
# 1) サーバー(別ターミナル)
python -m cucco.server.app

# 2) 評価モードで卓を作る(200ゲームを自動連続)
python -m clients.mock_ai.mock_ai --name Mine --create \
    --mode evaluation --game-count 200 --policy zemi_yourname

# 3) 表示された room_id に対戦相手を参加させる(人数分くり返す)
#    参加する側にも --mode evaluation を付ける(下記の注意)
python -m clients.mock_ai.mock_ai --name Rival --room <room_id> \
    --mode evaluation --policy matrix
```

全員が揃うと自動で走り、終わると成績が配信される。あとから見るには:

```bash
python -m cucco.tools.stats --policies      # 方策別の通算成績
python -m cucco.tools.stats --evaluations   # 評価モードの実行一覧
```

> [!WARNING]
> **参加する側にも `--mode evaluation` を付ける。** 付け忘れると、そのクライアントは
> 1ゲーム目が終わった時点で卓を離れてしまい、残った人数が足りずに評価が途中で
> 打ち切られる(`games_played` が指定より少ない結果になる)。

> [!IMPORTANT]
> **1回の結果で判断しない。** 人数と相手構成で優劣は桁違いに変わる。何ゲーム必要か、
> どう比べるかは [ai-advanced-policies.md](ai-advanced-policies.md)「検証の作法」に
> 実測付きで書いてある。

### サーバーなしで速く測る(`tools/fast_eval.py`)

上の手順は 1秒に8ゲームほどで、勝率 0.5pt の差を見るには遅すぎる。
`tools/fast_eval.py` は同じ対局をサーバーなしで回し(8コアで約400ゲーム/秒)、
**同じシード・同じ席**で基準と候補を入れ替えて差を取る。

```bash
python tools/fast_eval.py --candidate zemi_yourname --panel
```

- `--panel` は相手の卓を4種類(conservative×3 / 混成 / matrix×3 / aggressive×3)
  回して平均する。**相手を1種類に固定して測らない。**conservative×3 相手に
  +0.8pt だった変更が、混成卓と matrix×3 相手では 0 だったことがある
- 読むのは「差」の行だけ。z が 3 を超えなければ差は検出できていない
- 勝率と平均順位は**別の目的**で、継続の判断では答えが逆になる。内蔵の
  `counting_win`(勝率)と `counting_rank`(平均順位)がその実例

### どこで勝率を落としているかを測る(`tools/decision_map/`)

「何を変えれば強くなるか」を当て推量で試すと外れ続ける(交換の厳密解は
-3.9pt だった)。`tools/decision_map/` は方策の判断を**1つだけ反転**して
そのポットの決着まで打たせ、最終1位の確率と期待順位の変化を測る。80万判断
ぶんを区分ごとに平均すると、今の方策が損をしている場所がそのまま表に出る。

`counting_sniper` に対してわかったこと:

- 札別・人数別のしきい値はほぼ最適(ずれ ±0.03 以内)。ここは伸びない
- **手番位置と先行席の様子を見ていないのが穴**。先に動いた席が全員
  ノーチェンジなら交換を増やし、大人の時間の先頭手番と交換が起きた後は減らす
- **継続は目的で答えが逆**。1位を数えるなら払う、順位を数えるなら守る
- 大差の首位で誰かが残り2枚以下なら、継続を降りたほうが勝率も順位も上がる

地図は候補を作る道具で、採用の根拠にはしない。作った候補は新しいシードの
`--panel` で確かめる。手順は [tools/decision_map/README.md](../tools/decision_map/README.md)。

### 勝率ではなく「判断の質」で測る(こちらが速い)

勝率は分散が大きい。実測では**勝率で3ptの差を見るのに約7,000ゲーム**必要で、
200ゲームの走行では5pt未満の差は何も言えない。局面を仕込んで厳密解と突き合わせる
方が速くて確実。

```bash
python tools/oracle_check.py --samples 300      # 交換判断(18,000局面・3秒)
```
```bash
python tools/continue_oracle.py --zero-cost 3   # 継続判断
```

「リグレット」は**選んだ手の敗北確率 − 最善手の敗北確率**で、小さいほど良い。
自分の方策を `policies/` に置いてあれば一覧に並ぶ。参考値:

| 方策 | 交換判断のリグレット | 継続判断のリグレット(チップ) | 勝率 |
|---|---|---|---|
| `counting_conservative` | 0.0032 | 0.543 | **27.4%** |
| `counting_exact` | **0.0000** | 0.543 | 23.5%(-3.90pt、SE 0.73pt) |
| `counting_aggressive` | 0.0172 | 0.061 | 23.2% |
| `matrix` | 0.0203 | 0.260 | 20.2% |

どちらのツールも `--selftest` で厳密解自体をモンテカルロ検算できる。

> [!WARNING]
> **リグレットの順と勝率の順は一致しない。両方のツールで一致しない。**
> この表の `counting_exact` は交換判断を厳密解そのものに差し替えた方策で、
> リグレットは**定義上ゼロ**である。それが据え置きの `counting_conservative`
> に 7,000ゲームで **-3.90pt(SE 0.73pt)**負けた。しかも**正確にするほど弱く
> なった**: 猫の自爆を数えない版は -1.79pt(SE 0.96pt)、逆に「札が割れている
> 席を未知の引きに数えない」補正まで入れた版は -4.03pt(SE 1.22pt)である。
> 継続判断でも同じことが起きている(最強の `counting_conservative` が継続では
> 最悪の 0.543。リグレット最小の形に差し替えたら勝率 -0.73pt、SE 1.04pt)。
>
> 原因は近似の精度ではなく**目的関数**にある。交換の厳密解が最小化しているのは
> 「このディールで**自分が**敗者になる確率」だが、弱い札を交換で他家に押しつけ
> れば相手の敗北確率が上がる。その価値をこの目的関数はまったく数えていない。
> 継続の厳密解が最大化している「ポット終了時の期待チップ」も、勝敗(順位と生存。
> 既定の終了条件は `chips_zero`)とずれている。
>
> **リグレットは「自分の見積もりが厳密解と合っているか」の診断であって、強さの
> 指標ではない。**下げても勝率が上がる保証はないし、実測では逆に下がった。
> 強くなったと言うには、結局**勝率を測るしかない**。

> [!NOTE]
> 厳密解は**1手先だけ**を見る近視眼的な最適解。ディール中の以降の交換・宣言は
> 考慮していないので、「ゲーム論的な最適手」ではなく「いまの判断材料で測れる
> 範囲での最善」である。

### 候補を並べて一番良いものを選んだ数字は、根拠にならない

候補を3つ並べて7,000ゲーム回し、一番良かったものが +1.76pt(SE 0.60pt)だった
としても、それは採用根拠にならない。**3つ引けば一番良いものは偶然でも上振れする**
からである。実例として、この手順で選んだクク宣言の方策(`counting_sniper`)を
**1つに固定して取り直したら +0.39pt(SE 0.40pt)まで落ちた**。

選抜と確認は分けること。

1. 候補を並べて、見込みのあるものを**1つ選ぶ**(ここの数字は報告しない)
2. 選んだ1つだけで**取り直す**。この数字だけを根拠にする

2走行で結論が変わるので、選抜の数字をそのまま書かないこと。

## 7. つまずきやすいところ

| 症状 | 原因 |
|---|---|
| 卓を作る画面に自分の方策が出ない | サーバーを再起動していない / 読み込みに失敗(サーバーのログを見る) |
| `--policy` で「unknown policy」 | クライアント側のカレントディレクトリに `policies/` がない(`--policy-dir` で指定) |
| 弱いはずなのに勝率が変わらない | `decide_change_ctx` と `decide_change` の両方を実装していて、`_ctx` 側だけが効いている |
| たまに変な手を打つ | 例外が出て既定値に倒れている(サーバーのログに `policy ... failed` が出る) |
| 卓が固まる | 判断の中で時間のかかる処理をしている。方策は即座に返すこと |
| 評価が指定より少ないゲーム数で終わる | 参加側の `--mode evaluation` を付け忘れている(1ゲームで抜けてしまう) |
